# 0010 — 消息消费与全局异步并发

DJ 是持续运行会话之间的消息中转，不是逐业务任务的执行器。入站消息先可靠入库、去重，再由全局有界异步消费者投递。正常模式不等待上条 AI 业务结束。

## 消费模式

- 默认 delivery_policy.busy=steer：目标空闲时开始一轮输入，目标工作中时调用已经确认的原生追加/steer 接口。accepted 仅表示原生接收，不能说业务完成。
- 显式 busy=queue：保留队列消费，等待目标空闲；原路由顺序和未知提交屏障继续生效。现有 delivery_mode=pull 与 subscription.pull/ack 保留。
- 私有 message_delivery.busy 可选择服务级统一模式并覆盖单条策略；未配置时使用各投递策略。max_in_flight=1..64 控制全局并发（默认64），不因模型长期工作占用传输槽。
- 原生工具没有经核实的忙时接收接口时明确 busy_input_unsupported；不能伪称已发送，不能退回新建 Agent 进程，也不静默替用户启用业务排队。用户可以明确选择 queue。

## 可靠性与授权

每条消息仍独立执行当前授权、实例门、精确会话/工作区/epoch 和输入预算校验，发送前持久化 submitting 与 attempt，收到原生确认即释放传输槽。不能等待模型结果或最终回答才释放。

一条 interactive 消息的 unknown/blocked 不阻塞同一会话其他独立 interactive 消息；该条 unknown 自身绝不盲目重发，沿原尝试核对。每条消息的幂等、回执与审计保留，不能用“直接发”省略持久切点。路由 claim 只保护短时传输受理，不构成业务任务锁。

Codex 工作中使用原 owner 的 thread-follower-steer-turn；空闲时使用已有 start-turn，继承原模型和权限，不取消原任务或自动批准请求。OpenCode 复用 prompt_async，Claude inbox 复用原生 priority=next 消息确认，不在 DJ 等空闲。它们的实际处理时点由原生接收端决定。其他端口未核实忙时接口前明确声明不支持，不能凭产品名猜测；该批真实忙时投递验收以现场实例证据为准。

## 停止与升级

DJ 退出只需排空自己尚未确认的传输/写入；已由 existing 原生客户端 accepted 的消息不要求等待模型业务完成。保留原投递和后续完成记录，重启不重发；不停止 AI 进程。submitting/unknown 仍必须安全核对，不能把不确定结果当成已接收。仅自有 managed 进程的销毁需要额外原生排空；该路径不用于当前生产装配。表情停止清理或租约到期不等于业务完成，原接收者随后仍可显式记录业务终态。

## 验证范围

验证默认 steer、显式 queue、全局模式/并发配置、忙时原会话精确投递、unknown 仅隔离自身、排队模式屏障保留和原生拒绝不冒充 accepted。复用必要回归，不将其他工具全矩阵或性能压力作为本批前置。

## 已完成验证

定向 Core/SQLite 集成验证已覆盖忙时追加、显式排队、单条未知结果隔离、全局消费配置和现有客户端的服务停止边界，关键原生 RPC 参数受保护性测试约束。本机服务已启用 steer、max_in_flight=64；真实 Codex 对话在首条维护输入仍工作中时，第二条独立输入获得 native_protocol accepted。接收不等于业务完成；其他工具的忙时能力按上文明确区分，不据此宣称全工具真实验收。

## 既有桌面会话的故障与重启恢复

- Codex 原生 `systemError` 表示上一轮失败；在已有接收端已恢复、没有权限请求、未确认提交或进行中回合时，允许向同一原会话提交下一条输入。历史窗口未加载完整不应把已终止回合永久判为忙碌。未知原生状态仍不当作空闲。
- DJ 运行期间桌面客户端重启，投递前先核对准确会话／工作区／命名空间，再独立核验同一端点的新进程标识。在原实例仍 ready、实例门仍 open、服务仍 ready 且所有权有效时，在同一写事务更新实例、门及会话标识；双重证据不一致、旧实例门已关闭或切换中的陈旧观测均不得放行。
- 不重建 Agent、不改订阅，不修改历史 attempt/binding，不重发 unknown。恢复后只继续原持久队列里尚未提交的独立消息；真实收件、订阅命中和客户端接收分别报告。
