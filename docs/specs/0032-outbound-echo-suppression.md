# 0032 DJ 外发回声不触发通知

## 行为

DJ发到IM的消息被WebSocket、HTTP补收或另一账号连接再次收取时，仍保存原消息、历史和引用关系，但不再由该消息创建新的AI通知。适用于私聊、普通群消息、话题及引用回复，默认自动执行，不要求AI增加过滤规则。

识别依据是DJ自己的持久发送动作和原生回执，不是正文、昵称、机器人类型或时间相近。因此人工发送的同文消息、人工@自己、别人的新回复及对原消息的表情/置顶动作仍是独立输入；指定表情标记继续按原规则触发。工作状态表情的自身回声继续由原工作表情登记识别。

这不是删除接收到的事件，不是禁止某个身份的所有消息，也不是把整个话题封禁。输入记录可供上下文读取，只有通知触发被抑制；原输入过滤、订阅、退订及0031的多线路通知归并分别保留职责。

## 模块与事务

- `messaging/service`编排发送状态与原生I/O。
- `messaging/echo`独立管理外发来源证据：发送前持久预留、回执登记、临时屏障及精确原生消息匹配。
- `connections/echo`只组合消息回声、工作状态表情回声及独立主动标记边界，给匹配、提交、pull和重放提供统一判断。
- 平台适配器只发送、返回原生消息/话题标识，不自己实现订阅过滤。

复用现有`echo_gates`和`echo_index`，不增加第二套去重存储。准备发送时，在同一事务提交outbound/attempt的submitting状态与屏障；原生I/O只能发生在其后。收到真实消息ID后，同一回执事务先建立精确回声索引再释放屏障。明确未发送释放屏障；unknown保留屏障、不得重发或当作未发送。已有重启恢复和核实路径复用相同证据。

## 回执前竞态

消息可能先经收件通道到达，再收到发送HTTP响应。已有准确会话的待定输入暂缓通知；新建话题时发送方尚无thread ID，改用发送动作的原生reply_to与收件parent/root关系识别，不能因为thread字段暂时不同而放行。

屏障不是永久屏蔽：回执明确后，只有精确原生消息被记为own_echo；同时暂缓的其他消息恢复普通匹配。话题根相同不等于所有后续消息都是回声。

## 原生命名空间

确认回执按原生消息ID匹配并核对平台、品牌、租户冲突及两端账号身份栅栏。Lark同一条消息跨私聊视图的chat地址投影不同，不可据此否认已确认的同一原生消息；其他平台继续保留原生会话命名空间检查。查询有明确数量上限，超过边界暂缓而不猜。

没有DJ发送回执的外部CLI或其他程序消息，不按正文伪造关联；通过DJ发送才有这项机械保证。该机制不宣称拦截外部工具的一切转发。

## 验证范围

业务实现后集中验证真实SQLite/Core的私聊、话题创建回执竞态、引用链、跨连接、重启后回声、明确未发送释放，以及相同话题内真正新消息继续触发；随后补关键匹配函数保护。原生IM端口使用可控协议替身，与真实平台收发证据分开。

本批结果：20项相关集成与12项保护检查全部通过，共616条断言。集成包含回执前独立连接读回屏障、新话题回声暂缓、回执后真实补充放行、私聊引用回应、重启后回声与人工同文新消息。平台命名空间、身份栅栏及独立触发边界由单测保护；不把协议替身结果当作真实IM新消息验收。
