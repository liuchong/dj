# 0003 — 扁平连接管理与消息路由

## 职责与数据

DJ 允许多个 IM、同一平台多个应用、多人授权登录，以及 user/bot 两种身份。它们是连接记录的数据差异，共用连接管理、入站接收、出站分发、人员识别和全局过滤；不按机器人名字或部署昵称编写产品分支。

只有一个扁平连接注册表。每条记录以不可变 `connection_id` 唯一定位，记录 `platform / brand / tenant_ref / account_ref / identity / identity_revision`，原生凭据只通过受保护引用装配。`connection_id` 不是人员 ID，不从其字符串推断平台或权限。同一账号可有多个连接，同一个人在多个连接中的原生身份由0002的服务级人员表关联。

消息地址沿用扁平 `{connection_id,native_chat_id,native_thread_id,thread_kind}`。人员身份与消息地址分开：人员决定“谁”，连接决定“使用哪个已授权账号”，原生会话/话题决定“发到哪里”。不能拿人员 OpenID 冒充 chat ID，也不能仅凭人名、群名或跨账号重复的原生 chat ID 选路。

## 单一路由与分发

- `createConnectionManager` 在服务启动时登记并装配连接；原生协议只在平台工厂中选择，不增设平台经理、身份经理或多层路由器。注册表拒绝重复/缺失连接 ID，未知平台不静默换适配器。
- `route(address)` 按显式连接及可选平台/租户/账号/身份/版本条件精确选择；零匹配返回 not_found，多匹配返回 ambiguous_target，冲突约束不回退另一个账号。此内部能力不替代公开操作的授权、conversation_ref 或 reply_context_id。
- `route` 也可带 `person_id`，通过共享人员表找出所选应用/租户下已核实的人员身份；多个账号可到达同一个人时仍返回 ambiguous_target，由调用方明确账号。返回原生人员身份不等于已解析私聊地址，不直接把它当作 chat ID 发送。
- `imPort` 是所有业务模块的统一连接定位入口；`dispatchIm` 统一执行原生接收和发送。原生接收的一页必须全部属于所选连接，不能按返回字段悄悄转投另一账号；发送记录的 connection_id 必须等于所选出口。
- 回消息使用持久来源地址和原 reply context，仍复核主体、连接身份版本及授权。明确的新发送必须先解析完整目的地；一个人跨多个 IM/账号可达时，不能自行选择“第一个可用账号”或在失败时改道重发。
- 用户账号/租户/应用变化仍触发已有 identity_revision 栅栏。旧事件缺少人员元数据时，只在事件与连接身份版本相同时恢复应用级身份作用域，不能按当前应用解释旧 OpenID。
- IM 连接统一初始化和关闭，重复端口对象只初始化/关闭一次，draining 结果继续向服务停止流程传播；现有持久队列、幂等台账、提交前后切点、ACK和断线恢复边界不改变。
- 全局人员/字符黑名单在接入持久化之后统一执行，不因连接数量、平台或 user/bot 身份而绕开。身份未核实不靠显示名猜测，缺失映射不能宣称已全平台覆盖。

## 本批范围

不新增中间服务、消息总线、平台 SDK、CLI 子进程或自动跨账号故障切换。公开接口继续使用明确的来源引用、目标引用和现有授权；平台接入可继续扩展，但不复制业务流程或人员黑名单。

## 本批验证

已完成定向Core/SQLite集成与关键保护性回归：4项通过、97个断言。覆盖两种Lark授权身份共享人员过滤、同chat ID在不同账号下的原生发送分流、原生接收入库、消息可见性、push/pull切点，以及多IM/多人候选歧义、人员按应用/租户选路、身份版本栅栏、跨连接返回拒绝和关闭幂等。不将受控原生接口的证据描述为真实外部账号全矩阵验收；未重跑全套、性能或AI工具验收。
