# 0004 — 对话规则持久保存与投递恢复

规则独立于聊天历史、订阅和定时器，按准确的 `session_key` 保存于DJ数据库；该键绑定工具、原生命名空间和会话ID，不按标题匹配。更换订阅、上下文压缩或重启不能删除规则；不同会话、工具或账号的规则不能串用。

- `revision/expected_revision`是当前对象的并发校验计数，不是规则发布版本，不提供历史规则或旧行为选择；项目只维护唯一现行接口。
- `session.rules.get` 用 `agent_id / session_ref / session_key` 三选一读取。空记录返回 revision=1、text=""。
- `session.rules.update` 使用相同目标选择器、`text`、`expected_revision` 与稳定 `idempotency_key`；同事务校验当前目标及权限、乐观锁和完整替换。UTF-8正文最多65536字节；清空使用空字符串。保存原文、SHA256、更新时间及修改主体，不自动改写、总结或执行规则。
- 读取需要 `session.rules.read`，修改需要 `session.rules.manage`，都授权到准确原生对话。知道对话ID不等于有权限；外部IM消息不能修改规则。规则不是审批、权限或仓库核心约束的替代。
- push和direct在提交前、pull在领取前，读取该目标的最新规则，将完整文本、当前并发校验计数、摘要和稳定session_key附入信封的`conversation_rules`。规则为空时不附该字段。原生帧超限则阻断并反馈，不截断规则。已提交或已领取的审计快照不回写；后续投递使用当前规则。
- 对话压缩或恢复时，Skill要求先读取 `session.rules.get`；每次投递携带规则便于恢复，不能承诺模型必然遵守。规则保存不等于实时触发覆盖，定时器暂停状态不因保存规则而改变。

业务实现后进行当前切片的集中集成验收，再补关键保护单测；不重跑全工具或性能矩阵。真实业务规则和账号资料只留本机私有数据库，不写入产品仓库或公共示例。

## 原文保存与可读性

- `text` 是会话自行编写的完整规则原文。建议使用 Markdown 标题、短列表或扁平键值及真实换行，避免把整份规则对象或正文重复 JSON 序列化后再作为 `text` 提交；这是一条编写建议，不是格式限制或自动转换功能。
- JSON 请求与响应中的标准转义由接口编解码处理；比较和恢复的是解码后的 `text`。保存后通过 `session.rules.get` 核对正文与 SHA256。字面 `\n`、反引号、引号及其他合法内容原样保存，不自动反转义、美化或重写。
- DJ 组装 `external_message` 通知信封；其中来源、上下文、订阅提示和回复凭证属于投递元信息，`conversation_rules.text` 才是会话持久规则原文。当前原生输入的单行 JSON 外壳由 DJ 生成，不能将它归因为会话保存格式，也不能声称仅调整规则写法就能消除该外壳。
- 通知信封与接口响应不要求 AI 的普通回复采用相同格式。普通回复建议使用自然语言；明确需要机器消费时才约定结构化输出。已有会话要求 XML 或其他输出格式时，其来源和修改权仍属于该会话规则，不由 DJ 自动覆盖。
