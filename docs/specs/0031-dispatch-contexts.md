# 0031 交互投递上下文与身份绑定

## 交付状态

源码实现跨连接通知归并、持久交互身份与显式转移；集成验收、安装采用及真实账号覆盖分别记录，不把源码存在当成服务已生效。

## 职责与对象

DJ 不推断任务、负责人或业务是否完成。交互投递上下文只记录原生消息关系、明确目标身份和实际投递事实。IM 来源线路、订阅条件、AI 接收会话与 IM 执行身份是四个不同概念。

- 来源线路说明某份数据由哪条连接收取；不能决定应由哪个账号回复。
- 逻辑事件说明发生了哪一次原生动作；同一消息的创建、编辑、表情标记及置顶是不同动作。只按已核实的原生标识和命名空间归并，不按正文、昵称或相近时间猜测。
- 交互上下文记录这次交互选定的 IM 账号及 user/bot 身份、绑定依据、原生锚点和转移记录；不是 AI 会话、物理连接或业务任务。
- 通知投递说明把哪个逻辑事件交给哪个准确 AI 原生会话。多个 AI 可分别收到，同一目标的等价线路副本只通知一次。

绑定账号身份不等于把一个 socket 永久绑定到对话；物理重连不改变账号。底层账号或授权主体发生变化时重新核验，不能凭连接 ID 沿用旧身份。

## 分层与调用方向

| 层 | 自己负责 | 不负责 |
| --- | --- | --- |
| 平台适配与连接 | 原生协议、认证、独立收件游标、发送、平台事实 | 订阅匹配、通知归并、交互身份选择 |
| 收件与消息存储 | 每条线路的原文、原生动作、来源及引用/话题事实 | 丢掉另一线路的历史、决定回复身份 |
| 订阅匹配 | 独立执行过滤条件，产出实际命中与指令 | 选择哪个账号处理、改变绑定、去掉其他接收者 |
| 交互投递上下文 | 事件等价关系、身份选择和持续绑定、显式转移、目标通知归并 | 理解任务、选择负责人、修改订阅与连接配置 |
| 传输与出站执行 | 按已冻结目标执行、记录 attempt/回执、恢复不确定结果 | 重新选择账号、因失败改道、重新推导订阅规则 |

实现将事件等价判断、绑定状态及转移、通知幂等分别组织为高内聚模块，共享明确的数据契约。投递执行只消费绑定结果；平台代码只提供原生事实。事务编排可以组合这些模块，不能把同一选择规则复制到收件、匹配、AI投递和IM发送各处。

## 绑定范围

默认沿准确的原生话题根、引用关系或原始消息锚点延续；独立群消息建立独立交互，不因群里一次 @机器人而把整个群永久绑定为机器人身份。私聊沿准确的原生接收账号及会话地址定位。无法证明关系的消息不按内容相似度接入原交互。

换 AI、转交对话、订阅更新或退订不隐含 IM 身份转移。调用方跨 AI 交接携带交互引用及原身份；DJ 只机械执行，不寻找或指定新的负责人。

## 首次选择与锁定时机

1. 收件与订阅命中只保存事实，不占有身份；不能先到的线路是谁，就认定谁负责。
2. 首次实际准备通知时，优先采用当前消息明确指向的已配置身份；@机器人选该机器人，@本人选该本人。无新指定时继承已存在交互绑定；尚无绑定时使用已核实的私聊接收身份、直接引用或话题原生目标。
3. 原生目标或可信映射尚未确定时保留未解析状态，不把缺映射解释成沿收件账号回复；输入通知与可用回复能力分别表述。
4. 在首次原生提交前，同一 SQLite 原子事务固定所选身份、依据、原生锚点和通知幂等占位。并发的另一线路读取原绑定，不能另选账号另发一次。
5. 原生确认接受后绑定生效并持续使用。明确未发送可以释放本次提交的临时占位；结果不明保留占位和身份，先核对，不换身份重发。

预留与生效属于投递事务状态，不是两套身份策略。绑定信息与每次实际投递的身份快照分别保存，不能以修改当前绑定改写既有记录。

## 持续使用与显式转移

| 情况 | 身份处理 |
| --- | --- |
| 同条消息晚到的 bot/user 副本 | 只补来源与匹配证据，沿原绑定，不再次通知 |
| 原话题/引用链内无新身份指定的补充 | 继承该交互绑定，继续通过同一账号身份处理 |
| HTTP补收、WebSocket重连、服务重启、AI离线恢复 | 恢复持久绑定与原投递状态，不重新选身份 |
| AI更换、换模型、换订阅、换接收对话 | IM身份不变；接收目标变化与IM身份转移分开 |
| 后续新消息明确 @另一个已配置身份 | 这是新的显式身份选择；在该新消息准备提交时记录转移，作用于该消息及之后的相应交互 |
| 调用方明确请求身份转移 | 机械核验目标账号、作用范围及当前绑定，记录显式转移；不根据自然语言任务含义推断 |
| 旧消息的迟到副本或重放观察 | 不能倒退或触发新的身份转移；使用它当时的绑定快照 |
| 当前账号暂时不可用 | 暴露状态并按原身份恢复，不自动改用另一线路的账号 |

同一条消息真正明确指向多个身份时，保留多个明确目标的事实，不按到达次序任意挑选、不把不同目标伪装成重复副本直接丢弃。此情况不能借“优先bot”或“优先user”制造隐式全局策略。

转移记录包括原身份、新身份、准确触发事件或显式请求、授权依据及生效边界。原已提交、accepted或unknown投递继续使用原快照，不被转移记录改写，也不重新外发。

## 通知归并与身份绑定分开

归并回答同一次动作是否已经通知该目标；绑定回答该交互由哪个IM身份处理。不能通过把 connection_id 塞进通知唯一键继续制造双份通知，也不能通过归并选出先到的账号作为回复身份。

默认不引入等两条线路到齐的时间窗口。第一份具备确定事实的通知正常提交，后来副本关联到原逻辑事件和交付记录；来源、订阅命中和触发依据保持可查。通知的唯一性需要持久原子约束，不能仅靠进程内集合或让AI自行防重。

明确的再次触发、不同动作、不同接收对话及独立分发意图继续分别处理。普通多订阅、组分发与输入/输出过滤各守原边界，本规格不修改业务规则、退订状态或可见历史。

## 实现验收边界

业务一次完成后，再集中验证双连接到达顺序、并发、晚到副本、提交前崩溃、原生结果不明、重启恢复、话题无@延续、明确换身份、旧消息晚到及跨AI交接；最后补纯函数和状态转换保护。实际原生消息、协议替身和服务投递记录分别说明，不重放业务消息冒充实时验证，不重复全工具验收。

## 当前接口与数据

- `dispatch.context.get`：`delivery_id` 或 `context_id` 二选一，读取持久绑定。
- `dispatch.context.transfer`：需要 `context_id`、`expected_binding_id`、`connection_id`、`explicit=true`、`reason` 和独立幂等键；复用原网络与消息回复权限，旧绑定引用继续校验自己的身份快照。
- `dispatch_contexts`保存交互当前绑定；`dispatch_bindings`追加每次明确身份选择与生效时间；`dispatch_notifications`持久占位并关联最多64份来源摘要，完整原始记录仍在收件及投递表内。
- push和pull分别管理通知消费；显式组分发按各自分发意图隔离。跨线路归并只使用已核验的相同原生标识、事件类型和命名空间；不能证明等价的动作不猜测归并。
- `delivery.get`公开 `coalesced_into`、身份绑定ID及 `notification` 来源关系。`coalesced`是独立终态，不伪造accepted或原生回执；unknown占位持续保护，明确未发送才可重新占用。

## 本批验证

5项新增集成覆盖双连接归并、绑定/显式转移及重启、unknown占位与人工无重试结案、明确未发送恢复、多接收目标、pull及组分发；4项保护性单测覆盖原生键、范围、64位顺序及接口参数。连同提及、表情、工作状态、多订阅和组分发回归共38项通过。Core和SQLite真实运行，原生AI/IM端口使用协议替身。引用DJ已发回复时通过发送回执和原回复引用定位交互，不依赖收件回显。

此记录不宣称崩溃注入、真实IM账号或全部工具矩阵已验证；实际部署、服务状态和Skill采用在交付时另行核对。
