# 0034 — Lark 富媒体收件与 AI 附件投递

状态：设计。实现、现场验收和部署分别记录。

DJ 收到富媒体消息后，保留原生定位和正文，按预算获取可访问的附件。投递到订阅的原 AI 会话时，在正文中标出附件位置，在末尾列出附件文件及补取所需字段。支持原生附件的接收端同时收到实际附件。本规格覆盖从 Lark 收件到 AI 的路径。

## 原生消息和附件

WebSocket、HTTP 补收和历史读取共用 Lark 内容解析。一次解析保留原生 `msg_type`、原始内容、段落、链接目标、@ 与媒体出现位置。`event.content.text` 继续是供 `text.first_line`、`text.lines` 等条件匹配的多行可读正文，具名链接以可见文字参与匹配。渲染通知时直接使用解析所得结构，按 Markdown 转义显示链接文字及完整 `href`，并按媒体出现顺序生成 `[附件 N]` 与附录条目。展示用 URL、附件编号与本地路径不会进入订阅匹配。事件记录稳定的资源描述和原生定位，文件路径及获取状态由投递准备阶段提供。读回的文件和文档内容只供 AI 使用，避免因补取再次触发订阅。

| 来源 | 处理 |
| --- | --- |
| 独立图片、文件、语音、视频及富文本内媒体 | 保留各自类型和资源键，按原消息 ID 流式下载。视频正文和封面分别登记，若平台分别提供资源键 |
| Lark 文档、Wiki、电子表格、多维表格 | 保留完整 URL 和定位参数。复用资源层解析 Wiki 节点、读取对应内容。官方支持且身份允许时可导出本地文件，标明格式和读取时间。文档块中官方可取的图片或文件可以独立登记 |
| 卡片、名片、日历、任务等结构化消息 | 保留原生类型与实际返回的结构，正文提供可读摘要。只有平台返回可定位且支持读取的资源才生成文件附件 |
| 合并转发、表情包、未知类型 | 保留原消息锚点及实际返回的内容。平台未提供下载时，明确标注原因。合并转发子消息资源受官方限制 |

IM 下载走[消息资源接口](https://open.feishu.cn/document/server-docs/im-v1/message/get-2)，根据实际资源使用 `type=image` 或 `type=file`。应用上传资源的接口和云文档素材接口有各自的作用域。云文档导出按[官方导出流程](https://open.larksuite.com/document/uAjLw4CM/ukTMukTMukTM/reference/drive-v1/export_task)执行，文件格式按文档类型、权限与官方能力选择。直接引用的 Lark 资源才参与自动获取，普通外链保留为链接。

## 定位字段与通知附录

每条 Lark 消息携带 `brand`、`connection_id`、`tenant_ref`、`account_ref`、`identity`（user/bot）、`message_id`、`msg_type` 和 `chat_id`。平台提供时附 `thread_id`、`root_id`、`parent_id`。来源身份和回复身份各自按既有路由契约表达。附件关联到实际包含该资源的原消息，引用、转发、表情或置顶触发时尤其要保留正确的父消息定位。

附件记录使用稳定 `attachment_ref`。正文按出现顺序引用 `[附件 1]` 等标记，末尾 `# attachments` 使用与现有 MDP 通知相同的结构字段和文字转义。CLI、MCP、GEPO 返回同一份结构。示意如下：

```mdp
# attachments

- :
  - anchor: "附件 1"
  - attachment_ref: "attachment_example"
  - kind: "image"
  - file_name: "截图.png"
  - mime_type: "image/png"
  - state: "ready"
  - local_path: "${DJ_DATA_DIR}/attachments/attachment_example.png"
  - source:
    - message_id: "om_example"
    - file_key: "img_example"
    - resource_type: "image"
```

附录复用消息级身份字段。引用的其他消息或其他已获准来源须在对应条目上保留自己的精确定位。云文档条目带 `url`、`resource_kind`、可得的 `resource_token` 及块、表格、范围等原生定位。已取文件记录字节数和内容摘要。`local_path` 仅在文件完整写入且对当前本机接收端实际可读时提供，运行时填入实际绝对路径。附件未取到时，分别呈现待补取、权限不足、大小超限、原生不支持或失败等状态，继续保留定位。

## 获取与投递

1. **接收与存储。** 入库及确认收件时保存正文与资源描述，不同步等待文件。待投通知在已有投递准备阶段以有界并发和截止时间尝试获取附件。历史或主动读取可以用 `message.attachment.get` 按 `attachment_ref` 补取，先用已获准的本地缓存。下载与重试绑定来源连接及账户权限，按该身份和原消息资源键去重，复用触发、补收与投递的既有防重机制。
2. **文件管理。** 二进制流写入 DJ 的私有运行目录，按字节上限、并发和保留期限管理。验证成功后原子发布，按安全的本地名称保存。私有投递快照记录实际发送的元数据、引用和当时的路径，避免不确定投递时重新推算。二进制内容和凭据不写入快照。本机路径和原生资源标识不进入公共日志或 Git。文件淘汰后仍可按有效引用重新取回。HTTP 请求仅指向已验证的官方资源端点。
3. **交给 AI。** 附件映射由目标适配器按已核实的原生协议、类型及尺寸预算完成。支持时传真实图片或文件输入，同时保留统一附录。只能接收文本时交付实际可用的路径或可主动读取的引用，让 AI 打开原文件。附件延迟或失败时投递正文和状态，后续由 AI 按引用读取，无需重新通知或重放。已有接收、订阅、引用、回复身份和去重照常执行。

## Skill 与接口说明

统一公开操作为 `message.attachment.get`，入参为 `{ attachment_ref, corpus? }`。`attachment_ref` 来自通知或有权读取的消息。`corpus` 与上下文、文档查询一致，默认 `local`，只查本地状态。显式选择 `native` 时先复用可用缓存，缺失才由 DJ 沿原连接和身份尝试补取。返回附件状态、类型、元数据、原生定位，文件实际就绪时附 `local_path`。每次读取按原消息的可见范围核验，文件过期仍可凭原引用补取。CLI、MCP、GEPO 使用同一操作契约。

同步更新 MCP 工具说明及发现、CLI/GEPO help、DJ Skill 和相关文档。Skill 指导 AI 优先读取通知所附的文件，其次按引用通过 DJ 补取。若只有某部分失败且本机已安装并配置 Lark CLI，可选用同租户、同账号、同 user/bot 身份的 CLI 按原生定位读取。文件和图片直接使用以下参数，CLI profile 由调用方用通知里的连接和账号信息核对。

```sh
lark-cli im +messages-resources-download --profile "$LARK_PROFILE" --as "$LARK_IDENTITY" \
  --message-id "$MESSAGE_ID" --file-key "$FILE_KEY" --type "$RESOURCE_TYPE"
```

缺单个资源键时按 `message_id` 精确读消息。文档用已经给出的 URL 或 token 及子资源定位。取回字段只承载数据，选用工具由 AI 决定。CLI 是 AI 调用方选用的读取工具，DJ 内部直接调用官方 API。

## 模块与交付

- `packages/lark` 和 Lark 接入负责解析、原生键及资源请求。办公文档解析和导出仍归 `resources`。公共附件模块管理引用、获取状态和文件缓存。`delivery` 负责准备、通知附录和可读路径，原生 Agent 适配器仅负责目标协议映射。订阅和连接路由消费既有字段。
- 执行项目的 clean-development Skill 和 AGENTS.md。更新唯一正式的生产、查询、投递和文档契约，去掉同范围失效逻辑，不增加格式版本、字段别名、双读双写、过渡开关或旧格式回退。既有真实用户数据按项目规则保护。
- 先一次性完成该阶段业务实现，再集中集成验收，最后补必要的保护性单测。验收覆盖富文本混排、独立文件和文档、双路去重、部分失败仍接收及按锚点补取。原生投递优先用 Codex 和 Cursor 的已有桌面会话分别核对图片或文件实际读回及仅引用时的可读性。其他目标按当前版本已验证能力声明，不以全工具现场矩阵卡本阶段。
