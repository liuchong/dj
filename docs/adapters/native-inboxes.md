# Existing Claude Code and Antigravity receivers

Both adapters connect to existing local processes only. They never start an Agent, restore one by argv, change its model or permissions, or use cloud control. AI-initiated DJ MCP/API and Skill installation remain independent of these outgoing transports.

## Prepare an endpoint

Run `dj native configure --input PRIVATE_JSON` with a private JSON file containing `tool`, `pid`, `directory`, `workspace_ref`, `instance_id`, `native_namespace`, `output_directory`, and `process_helper_ref`. The helper is the package's `libexec/dj-process-info`. For Antigravity include the observed local `base_url`; for Claude include its native `registry_path`. `--help` shows the fields. All paths are operator-selected local paths; no process is launched by this command.

The command verifies the same-user PID, executable, process birth and actual listening socket. It creates a new owner-private `endpoint.json` and refuses to overwrite it; Antigravity CSRF credentials are discovered only in memory. Merge the endpoint object into `agent_endpoints` in the service configuration explicitly. It does not modify client settings, subscriptions, permissions or trust. When an already configured client restarts on the same machine under the same UID, the shared local/Electron endpoint resolvers (`local-endpoint-resolver` and `electron-recovery`) and `lifecycle/native-refresh` re-verify the unique replacement process, listener/socket/window and exact original session in memory without mutating `endpoint.json` or restarting DJ; configure a fresh endpoint only when binding a different workspace, window or session target.

## Antigravity

The endpoint targets the existing App language server's Connect JSON API on loopback HTTPS when that process exposes the authentication argument used by this adapter. Runtime discovery reads the argument in memory and captures the public TLS certificate. Authenticated requests use the exact certificate as CA and pin its SHA-256. Every call rechecks PID birth and listener ownership.

Antigravity Desktop 2.34.0 keeps that credential inside the App and its language-server process. A matching desktop process without the required authentication yields `agent.discover` source reason `antigravity_desktop_auth_unavailable` and partial coverage, even when enumeration has ended. That state means live discovery, creation and delivery are unavailable. Both the App and DJ can stay running. An AI already working in the App can still initiate calls to DJ via its configured MCP server. [Antigravity MCP documentation](https://antigravity.google/docs/mcp?app=antigravity)

When connected, discovery uses native trajectory summaries restricted to the exact workspace URI by default, or across all verified local workspace directories of that language-server instance when `workspace_scope: "instance"` is configured on the endpoint (preserving each trajectory's real `directory` and derived `workspace_ref`). Probe uses current cascade status. Sending reads the latest user configuration from at most 128 native steps, preserves its actual model and configuration, and submits `SendUserCascadeMessage` with `NEXT_INVOCATION` for busy-input/steer or `WHEN_IDLE` for explicitly queued idle input. A running cascade accepts steer without waiting for the whole model turn; permission/unknown states are not treated as busy-capable. This is the native service strategy, not an SDK restriction. A route consumer drains up to 32 pending messages per job, preserving separate durable attempts and native acknowledgements; larger backlogs continue in bounded jobs. It does not combine business tasks or promise one model turn. Already accepted/unknown submissions are not replayed. An API acceptance is not model completion. A missing model/configuration or an oversized tail refuses the send before transmission; ambiguous transmission remains unknown and is not retried.

Message reads cover a bounded native tail, not full history. They use `GetCascadeTrajectorySteps`, preserve real native message IDs, omit thinking and tool content, and enforce a 1 MiB response ceiling. Cursors bind the original session and step offset; a stale cursor beyond 128 steps must be refreshed. Full-history coverage, native idempotency, instance lifecycle control and completion observation are unsupported; native StartCascade creation and annotation rename are supported (spec 0030). Receipt keys correlate DJ dispatches; they do not invent a native message ID.

### Shared client restart recovery

Existing-instance adapters share one capability-gated lifecycle refresh contract (`capabilities.instance_epoch_refresh = "supported"`) plus two local rediscovery layers:

- `local-endpoint-resolver`: validates cached process/socket/manifest identity, deduplicates concurrent rediscovery per `instance_id`, verifies that the prior `(pid, birth)` has exited before rebinding, locates the unique replacement same-UID process/listener/registry/manifest (Antigravity language server + leaf TLS certificate + memory CSRF token, Claude Code session registry + Unix socket, Kimi Work/Web registry, DSH Desktop/Web loopback host, Pi private receiver manifest), and re-verifies process identity before caching in memory. No refreshed credential or runtime endpoint is written to disk, SQLite, notifications or logs. Discovery never launches a client and fails closed on zero or multiple matches.
- `electron-recovery`: rebinds a restarted same-UID Electron main process and matching window for Cursor and Claude Desktop only after the bound `(process_id, process_birth)` has disappeared, preserving window URL and workspace checks.

Read-side `probe` and `probeInstance` observe the live `instance_epoch` of the exact original session without failing on a stale `binding.instance_epoch`, allowing `agent.probe`, `session.probe` and pending dispatch recovery to advance the instance gate and binding automatically without reconfiguring DJ or recreating subscriptions. Write and cursor operations (`submit`, `create`, `lookupCreate`, `rename`, `readMessages`) strictly enforce `expected_epoch`. Explicit stopped gates remain closed; historical bindings/attempts and accepted/unknown receipts are never modified or replayed.

## Claude Code

Requires a running Claude Code with native cross-session messaging and `notify_idle` support, its PID registry, and its actual Unix socket. A running Claude Desktop chat window or an old JSONL alone is insufficient. No Channels opt-in, Remote Control, pairing, extension, permission relay or new CLI is substituted.

DJ creates only its own private callback socket in the existing native socket directory, using its own PID. It sends native `msgV:1` frames with its truthful `uds:` reply address and no impersonated permission mode or child token. `notify_when_idle` provides bounded native idle evidence; one outstanding watcher per receiver avoids accumulating subscriptions. Sending requires fresh idle evidence and uses the existing target's accept/hold/refuse policy. Only correlated `peer_message_status: delivered` is accepted; held/no ACK is unknown and never automatically resent. Explicit denied/refused/expired/dropped outcomes are final. Late delivered receipts support positive-only lookup within bounded process-local retention; restart cannot reconstruct them and returns unknown.

Optional registry-bound JSONL reading is a bounded tail of the original session's user/assistant text, with native IDs and byte-offset pagination. It is never proof of a live receiver. Thinking and tool blocks are excluded. Closing the adapter removes only its own callback inode and never stops Claude.

Native protocol reference: [Claude Code cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging). Real-client results and missing receivers are recorded separately from local protocol fixtures in the delivery report.

## Claude Desktop and Codex native host control

Codex loads DJ’s receiver into its already running native Node tool host and explicitly configures control_manifest_path (see connectors/codex/README.md). It calls the official local App Tools pipe under the real host signature. For Claude Desktop use `dj native configure` with `tool=claude,surface=desktop`; its existing renderer exposes the native LocalSessions API. Creation, rename and resulting session IDs are verified; no new CLI/App Server, cloud endpoint or App Tools peer impersonation is used. The shared on-demand Inspector transport verifies same UID, process birth, time origin and window, and closes only the Inspector it opened. An occupied Inspector/debugger is an explicit conflict.

Codex keeps its existing follower socket for normal delivery; native host control supplements creation/rename. Claude Desktop supplies its own discovery/read/send APIs, distinct from the native CLI inbox above. `workspace_scope=instance` permits explicit absolute workspace selection on the same verified host. Empty native creation does not imply model execution; explicit first input is a separate durable delivery. See [0030](../specs/0030-native-session-creation.md).
